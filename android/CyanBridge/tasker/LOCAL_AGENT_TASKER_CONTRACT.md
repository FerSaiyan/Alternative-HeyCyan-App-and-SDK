# CyanBridge Local Agent ↔ Tasker contract

This branch moves Local Agent screen observation and every model-selected Android device action to a user-owned Tasker/AutoInput workflow. CyanBridge keeps task state, planning, risk classification, approvals, recovery, model inference and debug history.

The architectural invariant is:

> CyanBridge decides whether an action should happen. Tasker performs Android observation/execution.

`wait` and `finish` are internal agent-loop controls, not external device effects, so CyanBridge consumes them directly.

## Transport

CyanBridge sends explicit broadcasts to Tasker (`net.dinglisch.android.taskerm`). Tasker replies to CyanBridge.

Contract version: `1`

### Observe request

Action:

`com.fersaiyan.cyanbridge.TASKER_AGENT_OBSERVE`

Extras:

- `contract_version` = `1`
- `request_id` = UUID generated by CyanBridge
- `callback_token` = per-request random token; echo unchanged
- `payload` = request JSON

Tasker runs AutoInput UI Query and obtains the active package and UI data.

### Local Agent package blocklist

The user-controlled Local Agent screen blocklist now lives in Tasker global variable:

`%CB_LocalAgentBlocked`

Use package names separated by commas, semicolons, spaces or new lines.

After AutoInput identifies the foreground package, the Tasker observation handler checks this list. For a blocked package it returns:

```json
{
  "success": false,
  "payload": null,
  "error": "blocked_package:com.example.app"
}
```

and does not return that screen's text/nodes to CyanBridge.

The old CyanBridge SharedPreferences blacklist is no longer a second blocking authority. This removes the need for CyanBridge to enumerate installed apps or request `QUERY_ALL_PACKAGES` just to populate a blacklist UI.

For an allowed app the observation payload is:

```json
{
  "created_at_ms": 1770000000000,
  "package_name": "com.example.app",
  "text_summary": "Optional bounded visible-text summary",
  "nodes": []
}
```

AutoInput fields can be reduced when unavailable; the CyanBridge parser tolerates partial nodes.

### Execute request

Action:

`com.fersaiyan.cyanbridge.TASKER_AGENT_EXECUTE`

Tasker is the execution target for all current model-selected device actions:

- Back / Home / Recents / Notifications
- text/coordinate clicks
- typing
- scrolling / long press
- app launch
- dialer, SMS and email composers
- alarms and contacts
- Wi-Fi/Bluetooth settings
- flashlight
- screen read-aloud

`press_enter` and arbitrary-coordinate `swipe` still return explicit adapter errors in v1 until their exact AutoInput export behavior is verified on-device.

Tasker remains an executor, not a second action-risk engine. It does not reclassify model actions or replace CyanBridge approvals. Package observation blocking is a source-privacy boundary: blocked screen contents are not returned to CyanBridge at all.

## Action consequence semantics

The profile intentionally preserves previous consequence levels:

- `make_call`: opens the dialer; does not auto-dial.
- `send_sms`: opens a composed SMS; does not silently send.
- `send_email`: opens the email composer.
- `set_alarm`: invokes Tasker's alarm action with confirmation/UI.
- Wi-Fi/Bluetooth actions open their settings screens.
- flashlight uses Tasker's Torch action.
- screen read-aloud uses AutoInput query + Tasker TTS.

## Response

Action:

`com.fersaiyan.cyanbridge.TASKER_AGENT_RESPONSE`

Preferred compact extra `response`:

```json
{
  "contract_version": 1,
  "request_id": "exact incoming request id",
  "callback_token": "exact incoming callback token",
  "success": true,
  "payload": "execution result or observation JSON",
  "error": null
}
```

CyanBridge verifies the request ID, callback token and contract version before completing the request. The bridge also accepts the older expanded extras for debugging compatibility.

## Approval behavior

CyanBridge continues to classify risk and own the pending-action UI. Approved or auto-runnable actions reach `TaskerExecutionBackend`; Tasker attempts execution and returns the concrete result.

This keeps the failure boundary clear:

- policy rejection/cancellation → CyanBridge
- package blocked before screen disclosure → Tasker observation result
- device execution failure → Tasker result returned to CyanBridge

## Current profile status

`CyanBridge_LocalAgent_Tasker.XML` implements the current observation/execution contract and `%CB_LocalAgentBlocked` source-privacy filtering.

Package installation, generic arbitrary intents and generic shell execution are not currently first-class members of `LocalAgentAction` / `LocalAgentUiControlProtocol`; adding them remains a separate protocol-extension pass. When added, CyanBridge should parse/classify/approve them and Tasker should execute them.

AutoDiary and Visual Diary now have separate Tasker profiles and are documented in `AUTO_DIARY_TASKER_CONTRACT.md` and `TASKER_PLUGIN_MIGRATION_PLAN.md`.
